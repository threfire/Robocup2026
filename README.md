# Robocup2026

## X42 CAN 速度反馈调度

### 已验证的问题

控制任务以 1 kHz 运行。早期实现每次速度反馈调度都会在同一个控制周期内连续向
4 个 X42 电机发送 `0x35` 读实时转速命令。

实际测试发现：四个电机同时接入时，始终有一个电机没有速度反馈；即使将总查询频率
降至 100 Hz，问题仍然存在。拔掉任意一个电机后，原本缺失的反馈会立即恢复。

这说明问题不在平均 CAN 总线负载，也不在 STM32 的接收解析或环形队列容量；已验证的
直接触发条件是四条查询命令在同一时刻连续下发，使 X42 应答链路出现瞬时调度/时序冲突。
仅凭该试验无法再区分冲突发生在 X42 内部应答时序还是总线短时竞争，需 CAN 分析仪才可
继续定位到底层原因。

### 当前方案

每个 1 ms 控制周期仅查询两个电机，查询组交替发送：

```text
0 ms: 电机 1、2
1 ms: 电机 3、4
2 ms: 电机 1、2
...
```

实现位置：

- `Mymode/control.c`：`Mecanum_RequestSpeedFeedback()` 维护 `1/2` 与 `3/4` 的交替。
- `Core/Src/main.c`：启动后每个 1 ms 控制周期调用一次查询函数。
- `Mymode/control.h`：`CHASSIS_SPEED_FEEDBACK_REQUESTS_PER_TICK` 设为 `2U`。

该方式将单次突发查询从 4 条降为 2 条，保持每个电机 500 Hz 的反馈查询频率。实测四个
电机的速度反馈均可正常获得。

### 约束

不要恢复为单周期连续查询四个电机。若后续修改查询节拍，应保持每次最多两个电机，或
在发送后留出足够时间让对应 X42 回包完成。

### 串口限制

2025 年主控核心板的 USART2 硬件链路不可用，串口通信功能不得分配给 USART2；在线调参使用 UART5。
